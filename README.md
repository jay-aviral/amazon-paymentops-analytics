# Amazon-style PaymentOps Analytics & Automation System

An end-to-end, reproducible analytics platform for **payment operations**, built as a Business Analyst portfolio project.
One command generates **1,000,000 simulated payment transactions**, cleans and loads them into a relational database,
runs reconciliation and root-cause analysis in SQL, and produces a management Excel report plus a Power BI-ready data model.

> **All data is fictional.** It is generated by a seeded random process to look like an Amazon-style marketplace.
> It is not connected to Amazon systems and contains no real customers or transactions. Findings describe the simulation, not Amazon.

```
 generate_data.py ─► data/raw/*.csv ─► etl_pipeline.py ─► MySQL 8 / SQLite ─► sql/*.sql ─► build_report.py ─► Excel report
 1M attempts, seeded   (dirty extract)   validate · clean ·   6 tables +        41 analysis      export_powerbi.py ─► Power BI CSVs
 + injected defects                      dedupe · reject ·    views             queries        powerbi/DASHBOARD_SPEC.md
                                         load · verify
```

## Quick start

```bash
pip install -r requirements.txt
python -m src.run_pipeline          # ~2 minutes: generate → ETL → report → Power BI export
pytest -q                           # 14 end-to-end tests (~10 s)
```

Outputs land in `output/`: `PaymentOps_Management_Report.xlsx`, `powerbi_data/*.csv`, `data_quality_report.csv`,
`rejects/*.csv`, `etl_run_summary.json` and (SQLite mode) `paymentops.db`.

**MySQL 8** (the intended warehouse):

```bash
docker compose up -d                                   # or use your own MySQL 8 server
export MYSQL_PASSWORD=paymentops                       # MYSQL_HOST/PORT/USER/DATABASE also supported
python -m src.run_pipeline --target mysql
```

The same SQL files run on both MySQL 8 and SQLite (a zero-install stand-in used for the tests and the default run).
`tests/` enforces that the SQL stays inside the portable subset.

|---|---|---|---|

| 2 | Which methods fail most? | `sql/04`, sheet *Failures* | **NET_BANKING 9.78 %**, EMI 9.47 %, DEBIT_CARD 7.78 % vs UPI 4.50 %, WALLET 2.77 %. Top 3 reasons = 53 % of failures. Seeded 15-Jul PayGate-B outage detected (46 % failures vs 6.5 % norm) |

| 4 | Which refunds are pending or delayed? | `sql/06`, sheet *Refunds* | 1,977 pending, **1,240 past SLA (INR 44.9 L)**; 10.3 % of processed refunds late; FAILED_PAYMENT_DEBIT worst at 29.5 % breach |

| 7 | What would reduce failures? | `sql/06`, sheet *Recommendations* | Smart routing / failover, incident alerting, auto-refund job, refund escalation queue. Sizing is assumption-based (editable yellow cells, live formulas): about INR 2.1 Cr |

## What makes it more than "a dashboard and some SQL"

* **Realistic dirty data, with ground truth.** The generator injects duplicates, key conflicts, orphan rows, negative amounts, future and out-of-order
  timestamps, inconsistent casing and amount formats, then saves the clean "truth". The ETL must recover it, and a test proves it does.
* **Seeded stories to find:** two sale events, a PayGate-B outage (15 Jul, 14:00-18:00), a net-banking issuer incident (8 Sep), reconciliation breaks,
  refunds concentrated in manual-handling reasons. Detectors in `sql/04` find both without being told where to look (the net-banking incident is small, so it ranks lower than the gateway outage).
* **Reconciliation rules defined once** (`sql/02_views.sql`) and reused by SQL, Excel, Power BI and tests, so the numbers cannot disagree.
  A test re-implements the rules independently in pandas and compares counts.
* **Hard gates:** ETL fails the run if row counts, control totals or any of 12 SQL integrity checks (`sql/07`) do not hold. Rejected rows are never lost: they go to `output/rejects/` with the rule that caught them.
* **Excel report with live formulas and native charts**, work lists for the operations team, definitions sheet.
* **Power BI package:** star-schema CSVs, every DAX measure, page-by-page spec, theme, and a check-list of figures that must equal the SQL.

## Design decisions worth knowing

* **1M = payment attempts** (rows in `payments`). Retries create several attempts per order, so there are ~967 K orders.
* **Rates are over attempts**; PENDING stays in the denominator, so success % + failure % is a little under 100 %.
* **Ageing "as-of" time** is the latest payment timestamp, so results are reproducible rather than depending on today's date.
* **Reconciliation tolerance** INR 1.00 (`config.RECON_TOLERANCE`); **stuck pending** > 24 h. Change them in `02_views.sql` and `config.py`.
* **Reduction %** in the improvement sizing are **assumptions**, not measurements. They are shown as inputs, never hidden.
* PayGate-B's higher failure rate (6.55 % vs about 5.2 % for A and C) is structural: excluding the 15-Jul outage hours it is still 6.49 %. The outage is a separate, short-lived spike. The routing query sizes the gap by method.

## Known limitations (read before an interview)

* The MySQL path (`--target mysql`) is implemented and the DDL/SQL stay within MySQL 8 syntax, but this repo was developed and tested against SQLite;
  run it once against your MySQL 8 and fix any dialect surprises before presenting it as MySQL-tested.
* The `.pbix` file is not included: it can only be created in Power BI Desktop. `powerbi/DASHBOARD_SPEC.md` is the build recipe.
* Synthetic data has no real-world seasonality, fraud rings or messy gateway behaviour beyond what is injected. Say so.
* Failure and break rates reflect the generator's parameters (`src/generate_data.py`), so the "insights" are recoverable by design. The skill on show is the method: define, detect, size, recommend.
